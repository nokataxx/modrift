# Development Process 個人モバイルアプリ開発プロセス

個人開発でのモバイルアプリ (iOS/Android、React Native + Expo) 開発の全体フロー。

- **作成日**: 2026-05-25
- **適用範囲**: 個人開発のモバイル/Webアプリ全般
- **前提技術スタック**:
  React Native (Expo) + TypeScript、TestFlight → App Store の配布パス

## 全体フロー

```
[Phase 0] 企画
[Phase 1] 要件定義
[Phase 2] 設計 (UI/UX + 技術アーキテクチャ)
[Phase 3] 実装準備 (環境構築)
[Phase 4] 実装
[Phase 5] 配布準備
[Phase 6] リリース (App Store公開)
[Phase 7] 運用・改善 (継続)
```

Vibe Coding においては、Phase2 ほぼ不要、Phase3〜4はAIの作業となる

## Phase 0: 企画 (Ideation)

**目的**: 「何を作るか」「なぜ作るか」を決める

### 成果物

- **アプリ名** (命名)
- **コンセプト** (1-2文で言える本質)
- **ターゲットユーザー** (自分自身 or 想定ペルソナ)
- **差別化軸** (既存アプリとの違い)
- **課金方針の粗い方向性** (無料 / 買い切り / Freemium / Subscription — この時点では仮で OK、詳細は Phase 5 までに確定。詳しくは「[課金設計のタイミング](#課金設計のタイミング)」参照)

### 作業内容

1. アイデアのブレインストーミング
2. 競合調査 (App Store, Web)
3. ターゲットユーザーの言語化
4. アプリ名の決定 (商標・既存サービス確認含む)

### ツール

- Obsidian / メモ
- 紙とペン
- ChatGPT/Claude との対話

### 目安期間

- 数日〜1週間

### 注意点

- 命名に時間をかけすぎない (最初は仮称でも進められる)
- 完璧な差別化を求めすぎない (実装で見えてくることも多い)

## Phase 1: 要件定義 (Requirements)

**目的**: 「何を、どこまで、どんな順序で作るか」を文書化

### 成果物

**Requirements.md**

主なセクション:

1. 概要 (Product Concept、名前の由来)
2. 背景・目的 (Why)
3. 想定ユースケース
4. 対応言語
5. スコープ (MVP / v1.1 / v2 / 意図的に実装しないもの)
6. 主要な設計判断 (検討経緯含む)
7. 機能要件 (FR-01, FR-02, ...)
8. 非機能要件 (NFR-01, NFR-02, ...)
9. 技術スタック
10. 制約事項 (Gotchas)
11. 受け入れ基準 (MVP リリース判定)
12. ロードマップ
13. リスク
14. 用語定義
15. 関連リンク
16. 改訂履歴

### 作業内容

1. 機能の洗い出し (思いつく順)
2. 優先順位付け (MVP / v1.1 / v2 / 意図的に実装しないもの)
3. 各機能の詳細記述 (受け入れ基準まで)
4. 設計判断 (検討した代替案、採用理由、トレードオフ)
5. 制約事項・リスクの整理

### ツール

- Obsidian / VS Code
- Markdown
- ChatGPT/Claude との壁打ち

### 目安期間

- 3日〜1週間

### 注意点

- 完璧を求めない (実装中に気づくことも多い、改訂版として更新)
- ADR (Architecture Decision Records) は個人開発では過剰になりがち、Requirements.md に統合してOK
- ファイル分割しすぎない (個人開発では1ファイルが管理しやすい)

## Phase 2: 設計 (Design)

**目的**: 「どう作るか」を視覚化・構造化

UI/UX と技術アーキテクチャの両軸で設計する。

### Phase 2-A: UI/UX 設計

#### 成果物

1. **画面リスト** (どの画面が必要か)
2. **画面遷移フロー** (どう遷移するか)
3. **ワイヤーフレーム** (各画面のレイアウト、粗くてOK)
4. **デザインシステム基礎** (カラーパレット、フォント、スペーシング)
5. **コンポーネント設計** (Button, Card, Toast等の基本部品)
6. **アプリアイコン** (Phase 5 まで先送り可)

#### 作業内容

1. 画面を全部列挙する (ホーム、設定、編集、プレビュー、ファイル選択 等)
2. ユーザーフロー図 (どの画面から始まり、どこへ行くか)
3. 主要画面のワイヤーフレーム (紙でもOK、Figmaで粗く)
4. カラーパレット決定 (Primary, Secondary, Background)
5. タイポグラフィ決定 (フォント種類、サイズ階層)
6. スペーシング規則 (8pxグリッド等)

#### ツール

- **Figma** (無料プラン、デザイン業界標準)
- **Excalidraw** (ブラウザベース、手書き風で素早く描ける)
- **紙とペン** (最も早い、最初の発散にはこれが最強)
- **v0.dev** (UIを生成AIに作らせる、Reactベース)

#### 目安期間

- 3-7日

### Phase 2-B: 技術アーキテクチャ設計

#### 成果物

1. **フォルダ構成** (`/src/screens/`, `/src/components/` 等)
2. **状態管理方針** (React Context, Zustand, Jotai 等)
3. **ルーティング設計** (expo-router での画面定義)
4. **データフロー** (ファイル読み込み → 表示 → 編集 → 保存)
5. **エラーハンドリング方針**
6. **ネイティブモジュール設計** (必要な場合)

#### 作業内容

1. フォルダ構成を決める (例: `src/app/`, `src/components/`, `src/hooks/`, `src/lib/`)
2. 状態管理ライブラリの選定 (個人開発ではContext + useReducer で十分なことも多い)
3. ルート定義 (expo-router の `app/` ディレクトリ構成)
4. データの流れを図式化 (Mermaid等)
5. エラー処理パターンの統一 (try-catch、Error Boundary)

#### ツール

- Markdown (TechnicalDesign.md or Architecture.md)
- Mermaid (図を Markdown 内で書ける)
- Excalidraw (図解)

#### 目安期間

- 2-5日

#### 注意点

- 過剰設計を避ける (将来必要になってから追加でOK)
- 状態管理は最初は最小限で (Zustand/Jotai は後から導入も可能)
- 個人開発なら 1ファイル長くてもOK、後でリファクタする前提

## Phase 3: 実装準備 (Setup)

**目的**: 開発環境を整える

### 成果物

- セットアップ完了したExpoプロジェクト
- README.md (開発環境セットアップ手順)
- EAS Build 設定済み
- Apple Developer Program 登録済み

### 作業チェックリスト

- [ ] Expo プロジェクト作成 (`npx create-expo-app modrift --template`)
- [ ] TypeScript 設定確認
- [ ] 主要ライブラリのインストール
  - expo-router (ルーティング)
  - expo-document-picker (ファイル選択)
  - expo-file-system (ファイル読み書き)
  - expo-localization + i18next (i18n)
  - 各アプリ固有のライブラリ
- [ ] Linter / Formatter 設定 (ESLint, Prettier)
- [ ] Git リポジトリ初期化
- [ ] README.md 作成
- [ ] .gitignore 確認
- [ ] EAS CLI インストール (`npm install -g eas-cli`)
- [ ] EAS Build 設定 (`eas.json`)
  - development プロファイル
  - preview プロファイル
  - production プロファイル
- [ ] Apple Developer Program 登録 ($99/年)
- [ ] Bundle Identifier 決定 (例: `app.modrift.ios`)
- [ ] Expo Dev Client ビルド (実機での確認用)
- [ ] iPhone 実機でDev Client 起動確認

### ツール

- Terminal
- VS Code
- Apple Developer Portal
- EAS CLI

### 目安期間

- 1-3日

### 注意点

- Apple Developer Program 登録は数日かかることがある (早めに着手)
- Bundle Identifier は後から変更困難 (慎重に決める)
- Expo Go では動かないライブラリ (例: react-native-enriched-markdown) を使う場合、Dev Client が必須

## Phase 4: 実装 (Development)

**目的**: 機能を1つずつ実装してMVPを完成させる

### 実装サイクル (各機能ごと)

```
1. 機能の小さな単位を選ぶ (例: 「ファイルを開く」
2. その機能のUIを実装 (ボタン配置、画面遷移)
3. ロジック実装 (Document Picker呼び出し、ファイル読み込み)
4. 実機で動作確認 (iPhoneで実際に動かす)
5. リファクタリング (コードを綺麗に)
6. コミット (git commit)

[次の機能へ]
```

### MVP 実装の順序例 (Modriftの場合、1-2週間)

| Day    | 実装内容                                              |
| ------ | ----------------------------------------------------- |
| 1-2    | プロジェクト初期化、ホーム画面、ナビゲーション        |
| 3-4    | Document Picker、ファイル読み込み、エラーハンドリング |
| 5-6    | Md レンダリング統合                                   |
| 7-8    | 編集モード、TextInput、編集⇄プレビューのトグル        |
| 9-10   | 自動保存 (debounce)、保存状態UI                       |
| 11-12  | 最近開いたファイルリスト、AsyncStorage                |
| 13-14  | i18n 統合、日英切り替え                               |
| 余裕日 | バグ修正、リファクタリング、実機検証                  |

### 開発のコツ

1. **小さく始める**: いきなり全機能ではなく、1機能ずつ
2. **早めに実機で確認**: シミュレータと実機で挙動が違うことがある
3. **コミットは頻繁に**: 1機能完成ごとにコミット
4. **テストデータを用意**: 開発中に使う Md ファイル等を準備
5. **エラーログを見る**: React Native Debugger、Console を活用
6. **詰まったらClaudeに聞く**: 個人開発の最大の武器

### ツール

- VS Code
- iPhone 実機 (Expo Dev Client)
- iOS Simulator (Mac の Xcode 付属)
- React DevTools
- Charles Proxy / Proxyman (ネットワーク監視、必要なら)

### 目安期間

- MVP: 1-2週間 (副業時間で)

### 注意点

- 完璧主義に陥らない (動くものを先に作る)
- 機能追加より基本機能の安定化を優先
- iOSのDeveloper Mode 有効化を忘れない (実機で動かす際)

## Phase 5: 配布準備 (Distribution Prep)

**目的**: TestFlight および App Store に出せる状態にする

### 成果物

1. **アプリアイコン** (1024x1024、各サイズ用に展開)
2. **スプラッシュ画面**
3. **App Store スクリーンショット** (6.7インチ、6.1インチ等のサイズ、最低6枚)
4. **App Store 申請文** (説明、キーワード、カテゴリ)
5. **Privacy Policy** (簡単なものでOK)
6. **EAS Build (production プロファイル) でビルド**
7. **TestFlight 内部配布**
8. **βテスター数名からフィードバック**

### 作業チェックリスト

- [ ] **課金方針の確定** (無料 / 買い切り / Freemium + IAP / Subscription) — App Store Connect の必須入力。Freemium / Sub なら Phase 4 で StoreKit 統合が必要。詳細は「[課金設計のタイミング](#課金設計のタイミング)」参照
- [ ] アプリアイコン作成 (1024x1024 PNG)
  - 外注も検討 (Fiverr等で$50-200)
- [ ] スプラッシュ画面デザイン
- [ ] App Store スクリーンショット撮影・編集
  - iPhone 6.7インチ (必須)
  - iPhone 6.1インチ (推奨)
  - iPad (iPad対応の場合)
- [ ] App Store 申請文の準備
  - アプリ名 (30文字以内)
  - サブタイトル (30文字以内)
  - 説明文 (4000文字以内)
  - キーワード (100文字以内、カンマ区切り)
  - カテゴリ選択 (Primary, Secondary)
  - レビュアー向けノート (テスト方法等)
- [ ] Privacy Policy 作成・ホスト
  - GitHub Pages、Notion等で公開
- [ ] EAS Build (production) でビルド成功
- [ ] App Store Connect でアプリ登録
- [ ] TestFlight に内部配布
- [ ] βテスター数名に配布
- [ ] フィードバック収集 (1週間程度)
- [ ] 重大なバグ修正

### ツール

- Figma (アイコン、スクリーンショット作成)
- ChatGPT/Claude (申請文の下書き)
- App Store Connect
- EAS CLI
- GitHub Pages / Notion (Privacy Policy ホスト)
- TestFlight アプリ (iPhone)

### 目安期間

- 1-2週間

### 注意点

- アプリアイコンは差別化の要 (時間をかける価値あり)
- スクリーンショットはユースケースを伝えること (機能の羅列でなく)
- 申請文は SEO 的な観点も意識 (キーワード)

## Phase 6: リリース (Release)

**目的**: App Store に公開する

### 作業

1. **App Store Connect で申請**
   - すべての必須項目を入力
   - スクリーンショット、申請文、ビルドを紐付け
   - 「審査に提出」をクリック
2. **審査対応** (通常1-3日、最大1週間)
   - リジェクトされたら理由を確認し修正、再申請
3. **承認後、リリース**
   - 「リリース日時を設定」 or 「即時リリース」
4. **公開後のメンテナンス**
   - クラッシュレポート確認 (App Store Connect)
   - レビュー確認・返信

### 目安期間

- 申請から審査完了まで通常1-3日、リジェクト時は1-2週間追加

### よくあるリジェクト理由と対策

- **機能不足**: スクリーンショット + レビュアー向けノートで明示
- **プライバシー問題**: Privacy Policy リンクを正しく設定
- **クラッシュ**: 申請前に必ず実機で全機能チェック
- **メタデータ不正確**: 申請文の誇張表現を避ける
- **Dynamic Type 非対応**: 文字サイズ変更に追従するように

### ツール

- App Store Connect
- TestFlight

## Phase 7: 運用 (Operation)

**目的**: 継続的なアップデートと改善

### 作業

1. **ユーザーフィードバック収集**
   - App Store レビュー
   - X/Twitter、ProductHunt 等のSNS
   - 自分でも使い続けて気づいた点をメモ
2. **バグ修正リリース** (v1.0.1, v1.0.2 等)

3. **次のフェーズ開発** (v1.1, v2 開発)

4. **マーケティング**
   - X/Twitter で進捗発信
   - ProductHunt 投稿
   - ブログ記事
   - 個人サイトで紹介
5. **App Store Optimization (ASO)**
   - キーワード調整
   - スクリーンショット改善
   - レビュー獲得促進

### ツール

- App Store Connect (クラッシュレポート、レビュー)
- X/Twitter
- ProductHunt
- Sentry / Bugsnag (クラッシュ監視、必要なら)

### 目安期間

- 継続的 (1ヶ月〜数年単位)

## 課金設計のタイミング

課金は単一フェーズの作業ではなく、Phase 0 から Phase 7 まで分散して考える横断トピック。各フェーズでの考慮点と「**いつ決める必要があるか**」を整理する。

### フェーズ別の考慮点

| Phase                  | 内容                                                                               | 必須度   |
| ---------------------- | ---------------------------------------------------------------------------------- | -------- |
| Phase 0 (企画)         | 課金モデルの粗い方向性 (Free / Paid / Freemium / Sub) を仮置き                     | 任意     |
| Phase 1 (要件定義)     | 課金候補ポイントを Requirements に書く (例: v2 で PDF 機能を有料化、等)            | 任意     |
| Phase 4 (実装)         | MVP は基本無料で進める。StoreKit 統合は MVP に入れない                             | 推奨     |
| **Phase 5 (配布準備)** | **課金方針を確定**: App Store Connect で価格 (Free / Paid) と IAP プロダクトを登録 | **必須** |
| Phase 5                | Privacy Manifest に課金関連の data collection を反映                               | 必須     |
| Phase 7 (運用)         | ユーザーフィードバックを見て、v1.1+ で課金パターン追加・調整                       | 任意     |

### 課金パターン別の実装コスト

| パターン            | 追加実装                                                           | App Store Connect 設定                                   |
| ------------------- | ------------------------------------------------------------------ | -------------------------------------------------------- |
| **完全無料 (Free)** | なし                                                               | 「Free」を選ぶだけ                                       |
| **買い切り (Paid)** | なし (App Store 側で課金管理)                                      | 価格設定 + Tax Forms + 銀行口座                          |
| **Freemium + IAP**  | `expo-in-app-purchases` 等で StoreKit 統合、購入状態の管理         | IAP プロダクト登録、Sandbox テスト                       |
| **Subscription**    | StoreKit 統合 + サブスクリプション期間管理、自動更新、レシート検証 | サブスクリプショングループ登録、価格階層、トライアル設定 |

### 個人開発のオススメ進め方

1. **MVP は完全無料で出す** — App Store 審査の通過性を最優先、課金の複雑さを排除
2. **リリース後 1-3 ヶ月、ユーザーフィードバックを観察** — 何に課金してくれそうかが見えてくる
3. **v1.1 / v2 で課金を追加** — 明確な「課金ポイント」が定まってから StoreKit 統合
4. **既存ユーザーへの配慮** — 「あとから有料化」は反発が大きいので、grandfather 措置 (初期ユーザーは無料維持) や、新機能のみ有料化等を検討

### 注意点

- **Bundle Identifier (Phase 3) と同じく「あとから変えにくい」**項目。完全無料 → 買い切りへの変更は既存ユーザー体験を悪化させるので、グレースフルな移行戦略が必要
- **App Store ガイドラインの制約**: アプリ内の機能・デジタルコンテンツへの課金は StoreKit (IAP) 必須。外部決済 (Stripe 等) は原則不可
- **Apple Developer Program の事務手続き**: 有料アプリ・IAP を出すには App Store Connect で Tax Forms と銀行口座を登録する必要あり (時間がかかるので Phase 5 着手前から準備)

## 各Phaseの目安期間 (個人開発、副業時間)

| Phase         | 内容                       | 目安期間    |
| ------------- | -------------------------- | ----------- |
| 0. 企画       | コンセプト、命名           | 数日〜1週間 |
| 1. 要件定義   | Requirements.md 作成       | 3日〜1週間  |
| 2. 設計       | UI/UX + 技術アーキテクチャ | 1-2週間     |
| 3. 実装準備   | 環境構築                   | 1-3日       |
| 4. 実装 (MVP) | コア機能の開発             | 1-2週間     |
| 5. 配布準備   | アイコン、スクショ、申請文 | 1-2週間     |
| 6. リリース   | 審査、公開                 | 数日〜1週間 |
| 7. 運用       | フィードバック、v1.1, v2   | 継続        |

**合計目安**: TestFlight 配布まで 1.5-2ヶ月、App Store 公開まで約3ヶ月

## アプリ開発のドキュメント構成 (推奨)

個人開発では以下の構成が推奨される:

```
プロジェクトフォルダ/
├── Requirements.md      (要件定義書、設計判断も統合)
├── TechnicalDesign.md   (技術設計、必要に応じて、Phase 2-Bで作成)
├── DevelopmentLog.md    (開発中の気づき、つまずきと解決策)
└── _daily/              (Obsidianのデイリーノート、思考の記録)
```

**実装リポジトリ側** (GitHub等で公開する場合):

```
project-repo/
├── README.md            (アプリの説明、セットアップ手順)
├── CHANGELOG.md         (バージョン履歴)
├── LICENSE              (ライセンス)
├── PRIVACY.md           (プライバシーポリシー、App Store公開時必須)
└── src/                 (ソースコード)
```

## よくある落とし穴と対策

### 1. 要件定義に時間をかけすぎる

**対策**: 完璧を求めず、80%できたら設計に進む。実装中に気づくことの方が多い。

### 2. デザインに時間をかけすぎる

**対策**: 最初は紙やExcalidrawで粗く、Figmaで詰めすぎない。React Native標準コンポーネントで十分美しい。

### 3. 完璧主義で実装が進まない

**対策**: 動くものを先に作る (Working Software First)。リファクタリングは後でいい。

### 4. App Store審査でリジェクト

**対策**: 申請前に Apple のガイドラインを軽く読む。シンプルすぎるアプリは機能不足リジェクトのリスクあり。

### 5. 個人開発の挫折

**対策**: 小さなマイルストーンを設定。毎週「先週何を作ったか」を可視化。Claudeと進捗を共有してモチベ維持。

### 6. デバイス互換性問題

**対策**: 最低でもiPhone 1機種、iPad 1機種で動作確認。Simulatorだけに頼らない。

### 7. 命名で時間を浪費

**対策**: 仮称で進めて、後で変更。決まらなくても1日以上悩まない。

### 8. 課金設計を考え始めるのが遅い

**対策**: Phase 0 で粗い方向性 (Free / Paid / Freemium / Sub) を仮置き、Phase 5 までに確定。Apple Developer の Tax Forms / 銀行口座登録は時間がかかるので早めに着手。詳しくは「[課金設計のタイミング](#課金設計のタイミング)」参照。
